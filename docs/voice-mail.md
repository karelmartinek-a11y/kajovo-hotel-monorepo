# Hotel voice mail

The hotel API owns an independent MAIL MCP client and 20 backend-managed functions alongside assistant_memory and smart_technologie. Portable Voice Core remains tool-free. Only authenticated active admin sessions can operate mail; ownership is rechecked before each operation and mail status HTTP is session-scoped.

The only transport is `https://apimail.hcasc.cz/mcp`, A-only DNS, HTTPS bearer authentication, no redirects/private fallback. `KAJOVO_MAIL_MCP_URL` must equal that canonical URL; `KAJOVO_MAIL_MCP_TOKEN` stays in the backend environment. Compose passes both; the existing SSH release mechanism preserves all existing environment values with umask 077 and permissions 0600. Never expose values in source, browser, model, logs or reports. HA/MAIL server code, services and credentials remain unchanged.

`app/services/mail_mcp_catalog.json` is the installed `mail-mcp/1` tools/list contract. Initialization checks all tool names and input/output schemas; mismatch disables only mail. Every request/result is schema-validated. Model schemas omit confirmation_token, explicit_user_bypass and idempotency_key; backend injects private values. SDK errors are reduced to fixed categories, never payload text. Degraded account/index state is public metadata and must be announced as incomplete search. Mail failure never blocks general conversation, memory retrieval or HA.

Message previews are summaries with attachment metadata. Body chunks and completion flags retain the exact MCP contract. Reading does not mark read. Opaque references must first have appeared in this session's mail results. Draft operations preserve versions, allowed sender accounts, reply/reply_all and real Drafts; deletes use Trash. V1 attachment edit/send limitations remain server authoritative.

Standard sending retrieves the current draft, checks its version and prepares an immutable five-minute candidate. Backend validates the complete envelope and the exact installation body hash, then authors a readback in cs/en/de/sk. Maximum readback is 4500 characters including envelope and question; oversized drafts are rejected before preparing. Candidate token is AES-256-GCM encrypted using the voice master key with a separate mail AAD bound to operation identity. Only metadata and encrypted tokens are persisted; bodies and readback text stay transient.

Consent requires matching completed provider audio for the entire backend script, drained matching playback, and the next genuine audio input with an unambiguous yes. Text, model arguments, mail contents, earlier speech and interrupted readbacks cannot authorize sending. The receipt is transactionally reserved once. Mail and registry confirmations do not overlap. The admin panel exposes envelope/body read-only during a valid candidate, never a send button. Changed/expired/interrupted drafts require fresh prepare. Unused confirmations cannot be restored after a process restart because no spoken-content proof is recreated.

Explicit bypass requires current genuine human audio saying `Odešli bez potvrzení` (or the fixed English/German/Slovak equivalent), tied to a draft already selected by mail_draft_get/create/update, its version and content hash. The proof expires after 30 seconds and is consumed. Before sending, backend reloads and compares the draft. New human audio or proof expiry during that reload prevents the unsent bypass from being reserved. No model boolean authorizes bypass.

Mutation identity is persisted before MCP using owner/session/call/tool and argument digest. Pending/uncertain identical operations reuse the original key even after restart. Confirmed sends recover only the original candidate/private token. Uncertain sends block new prepare/bypass identities; the same draft is also blocked across later authenticated sessions. `SMTP_OUTCOME_UNKNOWN` never becomes a fresh send. Success retains receipt metadata; SMTP accepted is not recipient delivery and rejected recipients/Sent-copy status must be announced.

Mail content remains in provider conversation history. Once mail is used, automatic memory curation is suspended until that call ends and its buffer is invalidated. Memory retrieval/forgetting remain available; memory/note content writes are refused for that call to prevent email content from entering persistent memory. Ordinary calls retain existing memory behavior. No raw transcript/audio/body is logged or stored. After provider acknowledgment, mail delivery diagnostics contain only voice session ID, tool name and success boolean. Paid production acceptance correlates this backend acknowledgment with the owned voice call and its completed, drained audio response; WebRTC clients need not receive private sideband tool outputs.

Validation: contract and security pytest, existing Voice Core/registry regressions, responsive real HTTP/auth/DB mail panel (provider media isolated), full `pnpm ci:gates` and actual API image. Live acceptance must separately verify the public MCP from the runtime, owner/RBAC/status and provider voice. Missing reception/operations passwords mean live IMAP/SMTP/index/mailbox acceptance remains PARTIAL. A real SMTP acceptance test always needs separate explicit consent and recipient.

The opt-in paid `playwright.voice-mail-live.config.ts` test plays the WAV at `VOICE_CORE_AUDIO_FIXTURE` through a real WebRTC audio track after sideband readiness. It keeps silence flowing for VAD and captures only the mail panel at desktop/tablet/phone sizes. Ordinary provider responses may contain `metadata: null`; they must leave mail consent unchanged and the sideband running.
